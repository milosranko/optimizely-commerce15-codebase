Problem 0.1: Dependency injection

    Level: Beginner

    The entire Episerver framework is built on the concept of Dependency injection. I would assume
    you know it already, but if you haven't, then this is a two cent definition (which is actually pretty
    good). A discussion can also be found here

    Then why dependency injection? One of most important features of Episerver framework is to allow
    you to overwrite the default implementation to let you do extra things. If you create a new instance
    like this:

1 var myNewInstance = new NewClass();

    It will introduce a hard dependency between your code and NewClass. So now if someone else use
    your code, and they need to do something that NewClass doesn't, they can't just replace that code
    with SuperNewClass. Remember Episerver products (CMS and Commerce) are frameworks, so you
    will have to extend them a lot (adding new features, integrating with external systems, changing
    default behaviors, etc), so you will almost certaily have to replace a default implementation, sooner
    or later.

    That's why dependency injection is important to Episerver, and that's why you will use it a lot.

    Before going deep into injection, there are 4 way of creating new instance of some class. Use of
    constructor above is one (and usually the worst way, when it comes to dependencies). The others
    are:

        · To use ServiceLocator
        · To use property injection, via Injected<T>
        · To use constructor injection

    And constructor injection should be the preferred method for injecting dependencies. When
    constructor injection is not possible, such as in a WebForm page (hey, why are you still using it?),
    the property injection should be used.

                     Some might argue that ServiceLocator and property injection are equally bad. That's a
                     valid argument if we consider dependencies should be transparent, i.e. if a consumer wants
                     to use a class, it should know what the class depends on, before hand. Both techniques hide
                     that from the consumer. However, in my opinion, you can have all property injections in
                     the beginning of your class, and when you read the class, you have a better idea what your
                     class depends on. For that reason, property injection is slightly better. Of course, they are
                     still not the best way and you should try to use constructor injection if possible.

Problem 0.2: Register dependency

Level: Immediate

In previous solution we were looking at getting instances from the dependencies. But there are many
places where you need to register your dependencies - to overwrite the default implementation.

There are two way to register dependencies - via attribute, and via IConfigurableModule. Let's go
through them one by one:

To register a class as a dependency, just add the attribute [ServiceConfiguration] to it, for example:

However, remember that this is only needed for implementations of interfaces, or base classes, for
example, this is not necessary:

1 [ServiceConfiguration(typeof(MyNewClass))]
2 public class MyNewClass
3{
4}

    The reason was the Inversion of Control framework (by default, structuremap) can figure out how
    to create an instance of MyNewClass when it's requested. However, if MyNewClass inherits from
    IMyNewInterface, and then when you request an instance of IMyNewInterface, the framework need
    to know which implementation you would want to use, so this is needed:

1 [ServiceConfiguration(typeof(IMyNewInterface))]
2 public class MyNewClass : IMyNewInterface
3{
4}

    What would happen if you have more than 1 implementation of IMyNewInterface? You can also
    register the other implementation with the attribute as well

1 [ServiceConfiguration(typeof(IMyNewInterface))]
2 public class MyOtherClass : IMyNewInterface
3{
4}

    Now if you request an instance of IEnumerable<IMyNewInterface> from the IoC framework, then
    both MyNewClass and MyOtherClass are returned. What what if you return just an instance of
    IMyNewInterface?

    There is no guarantee for such order. The behavior of the IoC framework is that the dependency
    registered later will be the "default" one. However, using attribute, there is no way to ensure the
Chapter 0: Preparation                                                                   6

order of the implementations being registered. In one start up, MyNewClass might be registered first
and then be overriden by MyOtherClass, but in another start up, it's vice versa. You of course don't
want to leave that to chance: it's frustrating that sometimes your feature works, sometimes it doesn't.
That's when you need the explicit registration.

This come to an interesting aspect if you want to replace the default implementation. If a default
implementation is registered via attribute, you can replace it with your implementation by an
IConfigurableModule. The discovery for attribute registration always happen before the execution
of IConfigurationModule, so your implementation will override the default one. Thing will get
more tricky if the default implementation is registered in an IConfigurableModule, you will have
to make sure that your IConfigurableModule is executed after that. This can be done by using the
[ModuleDependency] attribute:

1 [ModuleDependency(typeof(Mediachase.Commerce.Initialization.CommerceInitialization))]
2 [ModuleDependency(typeof(DataInitialization))]
3 [InitializableModule]
4 public class MyInitializationModule : IConfigurableModule

However, it's very hard to know which dependency was registered by attribute, and which was by
IConfigurableModule, so as a rule of thumb, you should make your IConfigurableModule to depend
on the lowest level module in the dependency chain. For example, your Commerce initialization
modules should depend on EPiServer.Commerce.Initialization.InitializationModule, because
it's the point when every Commerce module has been successfully initialized, and all default
implementations have been registered.

Problem 0.3: The dependency lifecycle

Level: Immediate
Not all instances are created equal. They are given different life cycles that will significantly affect
how many of your instances will be created, and if they are shared between sessions/users.
4 most important lifecycle in CMS 10:

   · Per request (or transient): A new instance will be created every time it's requested.
   · Per session: A new instance will be created once per Http session.
   · Per hybrid session/thread: A new instance will be created once per Http session. If there is no

      Http session (for example, while a scheduled job is running), it will be stored in the thread.
   · Singleton: Only one instance will be created during the life time of the website.

Take your time to think about which lifecycle you want to use. Per request is the default if you dont'
specify any lifecycle. However, if the constructor is expensive to call, or an instance can take a lot
of memory, it might be a better to have your instance "cached"
Chapter 0: Preparation  7

Singleton should only be used if the your class hold no states (so it would be safe to be shared
between threads), and if it is expensive to construct an instance.

It's also important to think if one of your instances becomes "singleton" unexpectedly. A common
scenario is that you have a singleton class A, which has dependency on another class B. Even if this
class is registered with Transient lifecycle, it becomes singleton because when an instance of class
A is created, it also created and referenced to an instance of class B. And because that instance of
class A is never changed, so does the instance of class B.

In short, dependency lifecycle can be complicated, so don't take it lightly. Take some time to make
sure your dependency life cycles are as expected, because otherwise they can create bugs that very
hard to find.

                 True story: Once we received words from an angry customer because apparently they saw
                 that end user information is shared, so when user A logged in, she can see the address of
                 user B. This is of course a breach of privacy and it turned out the the singleton life cycle was
                 overly used, even for the object that holds the current user address. Yes, it is shared between
                 all users. Moral of the story: Singleton has it uses, but just don't overuse it.

Level: Beginner

When you integrate Episerver Commerce with an external system, such as an ERP or PIM system
it's common to identify a specific content, likely an entry. Normally, you are given a code, in form
a string, and you will have to get the content. How?

Let me introduce you a new friend: ReferenceConverter

This small (it's not so small like before) allows you to convert between code and ContentReference,
and vice versa. To understand these conversions, we need to understand how Episerver Commerce
works with identity.

There are 3 ways to identify a catalog content:

   · ContentReference, to identify a content through APIs. The ContentReference is only unique
      within a system, and it consists of three parts: The Id of the content, the WorkId of the
      content (can be empty), and the provider name (can be empty, in case of default CMS
      content). An example for catalog content ContentReference is "123_456_CatalogContent".
      "CatalogContent" is a constant for all catalog content.

   · The code. This is what external systems - price system, inventory system, etc. - understand.
      As we will learn later, this is used to handle prices, inventories, as well as lineitems. Note that
      code is only for Entry and Node, while Catalog uses Name.

   · The guid. This is an internal identity (although it's supposed to be unique globally). For
      example, when you add a link to a catalog content to a ContentReference property, the
      ContentReference will be saved to database as permanent link - so the guid will be used to
      permanently identify the content. Like code, guid is permanent and should not be changed.

Now consider these scenarios:

   · If you have a ContentReference, how to get the code of the product.
   · If you have a code of a product, how to load it. (if you already have a ContentReference, it is

      easy.)
   · If you have a Guid of a product, how to load it.

The preferred way of doing such things is by using IContentLoader - or the combination of
IContentLoader and ReferenceConverter. IContentLoader already has methods to load contents
by a ContentReference, or a Guid, so that's the easy part. Other than that, ReferenceConverter can
be used to get the code from ContentReference:
Chapter 1: Catalog System recipes                      9

1 var code = referenceConverter.GetCode(contentLink);

    and

1 var contentLink = referenceConverter.GetContentLink(code);

    Simple, right?

    You might not believe the number of times I saw code sample to load the content to get the code
    from the content. While loading content seems to be easy and cheap to do, but thousands or tens
    of thousands of such API calls will be a significant cost, both in term of IO and memory (contents
    are supposed to be cached). ReferenceConverter is much more lightweight and faster - so use it
    whenever possible. Even better, it also has APIs to get codes or content links in batches - which
    mean you can have even better performance by reducing the overheads further.

                     One of the most important tips for great Commerce performance is to know which APIs to
                     use. For that purpose, I'd suggest you to go through the developer guide, once. I know the
                     documentation can be boring and dry to follow, but it can make a big impact in your daily
                     work. Trust me, your effort will be rewarded.

Problem 1.1: Get all catalogs

Level: Immediate
From time to time, you will need to get all catalogs in your site. How? As previously stated, the
catalog system is fully integrated to content provider system, so to get all catalogs, you would need to
call IContentLoader.GetChildren of the parent content. But what is the parent content of a catalog?
All of the catalogs are direct children of RootContent. This is a virtual and unique content that is not
saved anywhere to the database, but rather, is constructed on-the-fly. IContentLoader.GetChildren
actually uses a ContentReference, how to get that of the RootContent?
ReferenceConverter comes to rescue. To get the ContentReference to the RootContent, you can use
ReferenceConvert.GetRootLink().

                 To be honest, GetRootLink() should have been a property instead. It returns same value all
                 the time, so it does not make sense to be a method.

The code to get all catalogs looks like this:

1 var catalogs = _contentLoader.GetChildren<CatalogContent>(_referenceConverter.GetRoo\

2 tLink());

    This code is actually with a gotcha. this overload of IContentLoader.GetChildren will use the
    current culture of the site to get the catalog. So if your site has en language as active language,
    but one of your catalogs is only available in sv language, you might be surpised to find that it will
    not be returned in catalogs. If you develop a site with a known set of catalogs (or may be just one),
    this issue can be discovered quite early. But if you are working on different catalog sets which are
    unknown when you build the site, or even more, if you are working on a framework level (like I
    am), then this can be well hidden from your testing, only to come back and bite you later. Solution?
    You should use the other overload of GetChildren which takes a LoaderOptions parameter, which

Problem 1.4: Choose an URL style

Level: Beginner

There are two url styles in Episerver Commerce, the hierarchical one where the urls reflect
the catalog structure, so it's in form of "https://yourwebsite.com/Catalog/Parent-Node/Child-
Node/Product". And the other one where you link directly to a product by a SEO URI "https://yourwebsite.com/produ
name". It's up to your business to decide which suite you most, but when you make up your mind,
you need to know where to change between style.
Chapter 1: Catalog System recipes                                             16

By default installation, the hierarchical url style is used. That is done by this registration in an
initialization module:

1 CatalogRouteHelper.MapDefaultHierarchialRouter(RouteTable.Routes, false);

    MapDefaultHierarchialRouter takes two parameter - a RouteCollection, and a boolean value to
    let the framework knows if you want to build outgoing URLs in SEO URI format. Then how to to
    switch to other style? When, you can simply use other method:

1 CatalogRouteHelper.MapDefaultHierarchialRouter(RouteTable.Routes, true);
2 CatalogRouteHelper.SetupSeoUriPermanentRedirect();

    Build it and tada! Now your products will be redirected to the Seo Uris.

  Problem 1.4.1: Switch between url styles

    Level: Immediate

    A very good thing about Episerver Commerce is that even you enabled the partial routing system,
    the old SEO Uri:s will continue to work (of course, as long as you keep the Uri:s unchanged. Episerver
    Commerce in particular and Episerver in general does not handle changed Uri:s). So they can coexist
    in same website - but that might not what you want - you might want to stick with only one routing
    system - it's been told that the more popular your URL is, the higher rank it gets in the search engine
    results.

    Redirecting all hierarchical urls to SEO Uri:s is easy, we just did it in the previous recipe. But
    vice versa it's tricky, there is no such built-in method allows us to do so. We can't even override
    SeoUriRouter because it's registered automatically and there is no way to guarantee that our router
    will be able to run before it. (If a matching router is found, the processing will stop). Let's explore
    other options.

    EPiServer.Web.Routing.ContentRoute has two events which might be interesting - RoutingContent
    and RoutedContent. As their names might suggest, the former is fired before any routers take place,
    while the latter is fired after that. We might not want to listen to RoutingContent because it's too
    early, we'll have to process all URI:s sent to our site, which will slow it down. It's better to only
    process after the URI has been routed successfully, we prefer it is processed by SeoUriRouter. We
    can do some checks and redirect if necessary.

    First, we need to register to RoutedContent event:

1 ContentRoute.RoutedContent += Routed_SeoUri;
    Chapter 1: Catalog System recipes                                             17

    And then implement it. It's another void method which takes an object as sender and an RoutingEventArgs
    as the EventArgs. RoutingEventArgs has SegmentContext property named RoutingSegmentContext,
    this is what we need. A successfully routed route will set the RouteObject of RoutingSegmentContext
    to the content it found. So we can check if that content is a catalog content or not, to see if we should
    redirect.

    But how can we know if the URI was SEO URI, or hierarchial URI? By checking for slash in the
    between? Not really effective, because the top level content only has one segment. We can mimic
    SeoUriRouter and try to load the Entry/Node by Uri? Yes that might work but it is not really fast. If
    we are lucky and the URI was SEO URI, the DTO should have been cached, but if it was hierarchial
    URI, we will have to hit the database to find nothing!

    Solution, well, HierarchicalCatalogPartialRouter will process to the last segment, and for each
    segment, the LastConsumedFragment is assigned to next segment, so it'll be empty at the end.
    SeoUriRouter, in other hand, does not really process any segment, so the LastConsumedFragment
    it returns will be the same path as requested.

    With that information, we can have this as our method:

1 private static void Routed_SeoUri(object sender, RoutingEventArgs e)

2{

3     var context = e.RoutingSegmentContext;

4     //RoutedObject is supposed to not be null here

5     if (!(context.RoutedObject is CatalogContentBase))

6     {

7        return;

8     }

9

10    if(string.IsNullOrEmpty(context.LastConsumedFragment))

11    {

12       return;

13    }

14    var urlResolver = ServiceLocator.Current.GetInstance<UrlResolver>();

15    context.PermanentRedirect(urlResolver.GetUrl(context.RoutedContentLink));

16 }

    And now we can redirect the SEO URI to Hierarchical URI in an effective way.

    Problem 1.6.2: Building the outgoing URLs

    Level: Immediate.

    In previous recipe we talked about multiple catalogs with same "UriSegment" - which we had a
    working implementation for incoming URL, i.e. when a customer visit a product url, we know which
    catalog we should choose from. But we still need to cover the generation of outgoing URL. I.e. when
    we link a product (For example, from a campaign page), we need to generate an URL which take the
    "catalog-less" pattern into account.

    We need to understand how the outgoing URL is built. The hierarchical router builds the URL by
    the RouteSegment of contents. However, we want to the urls appear to have same catalog, so the
    RouteSegment part for the catalogs must be the same, regardless of the true catalogs. Because all
    catalogs are on same level, their RouteSegment must be unique - and this is enforced from Framework
    level (which is understandable, otherwise, how can it know which content to choose). We can't also
    rely on name, which is required to be unique.

    What can we do?

    Well - we already have magic router which automatically figures out which catalog to use regardless
    of the RouteSegment for catalog, so we can just return some magic value. The tricky part is to
    know which method to override. Luckily for us, Commerce provides us TryGetRouteSegment, which
    returns the RouteSegment of a content in a specific language.

Problem 1.7: Get products belong to a specific market

Level: Advanced
It's great if you have a comprehensive reporting system connected to your Episerver Commerce site.
But if you don't, then there are time when you have to create the reports yourself. Let's consider
one type of report that would be to find out which products belong to a specific market.
   Chapter 1: Catalog System recipes                31

   This would be fairly easy if you use the recursive approach we talked about earlier. Just get every
   entry and check for MarketFilter. If this list contains the market id you are looking for, then add it
   to our list.

   Sounds simple, right? But if you want to have a few hundred thousands of products, this barely
   works effectively. Loading that much of products will be a waste of time and resource. As always,
   when the APIs can't provide an adequate performance, it's time to step up our game and do what
   is not (officially) supported.

   To make it work, we need to need to understand about the underlying type of markets - dictionary
   types. Like it or not, you will have to work with dictionary types, sooner or later. They can be
   particularly useful when you need to check something - fast.

   · For single value dictionary type, that number is the MetaDictionaryId of the selected value in
     MetaDictionary table.

   · For multi value dictionary type, things are a bit more complicated. That number is the MetaKey
     value in MetaKey table. This MetaKey, is, however, connected to MetaMultiValueDictionary,
     which itself points back to MetaDictionary. An "usual" design for 1-n relation in database,
     right?

   · For string dictionary type, it's more or less the same as multi value dictionary. However, the
     MetaKey will point to pairs of key and value in MetaStringDictionaryValue table.

   Those information might not be really interesting to you - but they can be useful in some specific
   scenario. Let's consider some of those cases:

   · You want to know which entries use a specific dictionary value. In previous example, we have
     a property named Color, we want to find all entries with Color is `Blue'. For front-end site, it
     would be easy to find such entries by search feature (will be discussed later), but what if you
     want to create a report for that? Episerver Commerce does not provide such functionality out
     of the box, so we'll have to craft it ourselves. Time for some SQL then!

    · Now let's go back to the original task we have. To determine which entries belong to which

    Problem 1.8: Move catalog items around

    Level: Immediate
Chapter 1: Catalog System recipes                                                               33

Catalog UI provides a very intuitive way to manage catalog items, including moving them around
(which is not just "by accident" - Episerver invested a fairly big chunk amount of time for UX
research, and then UI refinements to make managing catalog items really works). But sometimes
it's not enough. "Sometimes people deserve more.". Sometimes people deserve to have their items
moved programmatically.

There are two way to move a catalog item around: by using IContentRepository.Move, and by using
IRelationRepository.UpdateRelations.

To use IContentRepository.Move, it is simple as this:

1 _contentRepo.Move(contentLink, destination, requiredSourceAccess, requiredDestinatio\
2 nAccess);

    requiredSourceAccess and requiredDestinationAccess are the required access level of the user
    performing this action on the source content and the target content, respectively. It's up to you to
    decide, moving a content is not technically deleting the old content and creating the clone of it in
    the new location, but rather, changing the relation between the content and old and new parent.
    There is no AccessLevel defined for such changes, so it's really a matter of perspective here.

    Or with IRelationRepository:

1 var relations = _relationRepository.GetParents<NodeRelation>(contentLink);
2 var relationToRemove = relations.FirstOrDefault(r=>r.Parent == oldParentLink);
3 relations.Remove(relationToRemove);
4 var relationToAdd = CreateNewRelation(contentLink, newParentLink);
5 relations.Add(relationToAdd);
6 _relationRepository.UpdateRelations(relations);

    Now the tricky part is CreateNewRelation. There are two kinds of relations you can create:
    NodeRelation - between a node and a node, and NodeEntryRelation - between an entry and a node.
    Just remember the bigger entity is Parent, and the smaller entity is Child. For example, to create a
    NodeEntryRelation:

1 var relation = new NodeEntryRelation();
2 relation.Child = contentLink;
3 relation.Parent = newParentLink;
4 relation.SortOrder = 10;

Strictly speaking, NodeEntryRelation extends NodeRelation, so NodeRelation can be used
to represent a relation between an entry and a node (and that still counts as a node relation,
literally). However, to make thing easier to understand and follow, you should always use
NodeEntryRelation to represent a node-entry relationship.
Chapter 1: Catalog System recipes                                                             34

Now we have a new node-entry relation, just add it to the collection and save. Now this is a bit
over complicated approach. You can just get the old relation and update Parent to point to the new
parent link. But keep in mind that is not completely bullet proof. In case you move an entry which
was a direct child of a catalog (i.e. it was not a child of any categories), then you will not find the
existing NodeEntryRelation, and will have to create a new one.

There are something you should keep in mind: IRelationRepository works in a lower level, so it
does not care about permission/access rights at all. It does not also fire content events (which you
usually listen via IContentEvents). In fact for catalog content, IContentRepository.Move used to use
IRelationRepository internally (That changed in Commerce 11). If such things are requirements
for you, then you should stick with IContentRepository.Move.

If you are using Commerce 10 or earlier, then I have bad news for you. You would have to
deal with Source and Target properties in Relation. I'm going to be honest with you: I can't
remember which is which and always have to go back to read documentations to remind
myself. That's also why you should upgrade to Commerce 11 or later, because the APIs have
been vastly improved. Source and Target have been obsoleted, and are replaced by Parent
and Child. Now it's much easier to understand which is which, because in a relation, the
"bigger" entity is Parent and the smaller one is Child. That's all you have to remember.

Problem 1.8.2 Set the primary node

Level: Immediate

In previous recipe(s) we talked about the relation between nodes and entries. You will soon realize
that an entry can belong to multiple nodes. And that is to solve a problem - how would you place
a GoPro in your catalog? Under "camera" category or under "sport gear" category? Duplicating the
entry to be in both categories is not the best solution, for obvious reasons. To solve it: well, just place
it under "camera", then link it to "sport gear" - or the way around. Problem solved?

If you upgraded from previous version, the parent node with lowest SortOrder relation will be
selected as the primary. That is not exactly how it should be used (we will get into that later). The
primary node can also be set by moving the entries in Catalog UI. When you move an entry from a
node to another node, the primary is updated to the new parent.

What if you want to set the primary node, programmatically?

This requires Commerce 11.2 at least. Previously you can add or remove a node-entry rela-
tion (via NodeRelation), but you can't set it explicitly to primary. This requires the new type
NodeEntryRelation which was introduced in Commerce 11.2.
Chapter 1: Catalog System recipes  35

1 var relations = _relationRepository.GetParents<NodeEntryRelation>(entryLink);
2 var relation = relations.First(r => r.Parent == parentLink);
3 relation.IsPrimary = true;
4 _relationRepository.UpdateRelations(relations);

    Basically you find the matching NodeEntryRelation and set the property IsPrimary to true, and
    then save it back.

                     You don't have to update the entire collection, you can save only the specific one _-
                     relationRepository.UpdateRelations(new [] { relation });

There are a few things to keep in mind:

   · An exception will be thrown if you try to save two or more relations of an entry with IsPrimary
      is true. An entry can only truly belong to one node (or none at all - in that case it is linked to
      all the nodes, its true parent is the catalog it is in)

   · A new set primary node will override the existing one, if any.

Problem 2.0: Update a price

Level: Beginner

Prices change every time and you would want to update your prices as they change - as soon as
possible. In many cases, the price updates are on individual prices.

It's very important that IPriceDetailService save prices as-is, but the interface which you (should)
use to load prices - IPriceService has a fairly special behavior when it comes to which prices to
keep and which prices will be ignored. I.e. the prices you save might not be the prices your end-users
see on your site. This behavior will be explained in detail, as well as how to change it, in later recipe.

To get a price, you have two options: load it by the Id, or load the entire price collection then filter.
The first option is actually almost impossible because you can't know the Id of the price you want to
update. (Well, unless that is synchronized with the external system you are using, but that is hardly
a good idea. Id is an automatically increased identity so there is no guarantee that it will never
change.)

                 It's important to remember that ContentReference is only unique within a system. It's not
                 supposed to be unique across systems. Entry code is used for that purpose, so when you
                 want to synchronize your data with external system, it's a good idea to use just code.

IPriceDetailService has several methods to load prices, but for our purpose, List(ContentReference

catalogContentReference, MarketId marketId, PriceFilter filter, int offset, int count,

out int totalCount) is the most effective because it limit the data being returned, because
the prices are filtered already at database level. Of course, you can use List(ContentReference
catalogContentReference) and then use LINQ to filter, but that would be slightly less effective.

Three last parameters are pretty self-explanatory - they are used for paging. First three parameters
are quite interesting:

   · catalogContentReference is of course the content link of the catalog item. Note that this is not
      the exact content link - if this is a product, then prices of its variants will be returned.

   · MarketId is the market to filter.
   · PriceFilter is a data class. You can specify Currencies, Quantities and CustomerPricing to

      filter prices. For example, if you want to get prices in "USD" and "EUR", then just set it like
      this:

    An empty filter value means nothing will be filtered. So if Quantities is empty, then your query

   Problem 2.1: Optimize prices, your own way

   Level: Advanced
   It can be quite confusing when you first edit prices in Episerver Commerce. To your surprises, some
   of the prices you imported or edited might disappear, or change, without your "consent"! What
   happened?
Chapter 2: Inventories and Prices.                                                            46

To answer that question, it's essential to know there are two pricing system in Commerce:
IPriceService and IPriceDetailService.

They have some different characteristics, and one of them is very important: the default implementa-
tion of IPriceDetailService saves prices as-is, while the default implementation of IPriceService
does not: it optimizes prices before saving. Prices which are best for customers will be favored over
the "less good" ones.

So here's an example of how it optimizes prices: Assuming you input prices like this:

   · Unit Price 100$, Valid From: 1/1/2017 to 12/31/2017
   · Unit Price 80$, Valid From: 4/1/2017 to 6/30/2017
   · Unit Price 60$, Valid Form: 5/1/2017 to 5/31/2017

The saved prices when you get back will be:

   · Unit Price 100$, Valid From: 1/1/2017 to 3/31/2017
   · Unit Price 80$, Valid From: 4/1/2017 to 4/30/2017
   · Unit Price 60$, Valid Form: 5/1/2017 to 5/31/2017
   · Unit Price 80$, Valid From: 6/1/2017 to 6/30/2017
   · Unit Price 100$, Valid From: 7/1/2017 to 12/31/2017

So the best prices in an overlapped period will be selected. While the behavior is reasonable (I
definitely like it, as a customer!), it might not be what you want. You might want to keep only the
highest prices, or you want to keep all prices - and leave it for some logic to decide which price
to pick. You can do the latter by using IPriceDetailService, but that is not without drawback:
the implementation of IPriceDetailService does not have cache, so it can have performance
implication as it will hit database every time. Also, it does not work in certain areas, because those
areas use IPriceService internally.

The only way to do it is to implement your own IPriceService. While the concept is simple (imple-
ment all the methods & properties, then register it in one of your IConfigurableModule), it's usually
easier said than done. IPriceService is a quite big interface - but you can probably rely on the de-
fault implementation (PriceServiceDatabase), and only implement SetCatalogEntryPrices(IEnumerable<Catalog
catalogKeys, IEnumerable<IPriceValue> priceValues) yourself.

It's worth noting that it's risky to rely on a concrete implementation, such as
PriceServiceDatabase, as it can be changed to be internal in future releases. It's easier to
use the intercept pattern, which is discussed in chapter 9.

However, it's still not a trivial or easy task. You will have to optimize the prices the way you like,
save it to database (you can call the existing stored procedure), and have to validate the cache for
updated prices. Too much issues for a seemingly small problem - and you are having to do stuffs
that you should not have to.

           A moment of truth here: a good framework is a framework which allows you do to
           certain implementation without having to do extra works unnecessarily. In many aspects,
           Commerce do that quite well, but not in every place.

    Worry no more. Commerce 11 comes with a new interface that allow you to control the optimization
    of prices, and it's a very thin interface.

    Problem 2.3: Change prices globally

    There might be cases when you want to change your entire store's prices. For example, if you are
    selling goods exclusively from a manufacturer, and they say that due to blah blah, the prices will go
    up. It's worth noting that as a customer, I'd like price drops, not the way around, so in this example,
    we will see how to cut prices of all products to 5%, instead of making them 5% more. Of course, it's
    just simple mathematics, so you can change to the formula however you want.
Chapter 2: Inventories and Prices.                                                          54

There are other times when you want to change prices globally, for example, you want to
give 10% discount for everything as a Black Friday sale. But those temporary changes could
be done easily by promotion system. We will get to it later.

    Let's go with the fast method first. The prices are stored in two systems, as we already know,
    IPriceDetailService and IPriceService. The unit prices are saved in PriceDetail, and PriceValue
    tables, respectively. Luckily for us, changing the unit prices does not involve reference tables and
    such, therefore it's a simple query

1 UPDATE PriceDetail SET UnitPrice = 0.95 * UnitPrice WHERE 1=1
2
3 UPDATE PriceValue SET UnitPrice = 0.95 * UnitPrice WHERE 1=1

    This should be very fast ­ but as always, this is something you should avoid. For starter, the prices
    are cached by default, those these changes are not visible in the application layer, unless you do a
    cache cleanup (read, IISRESET) for your site.

                     You can technically remove the master cache key for prices, which would invalidate all
                     prices. However, that is not disclosed by Episerver documentation. Cache handling is
                     difficult and can be tricky to get right.

Secondly, updating prices are supposed to fire certain events. By skipping that parts, listeners from
framework or 3rd party library might behave incorrectly. Also, in next version of Commerce, the
database schema might change, render that queries above invalid, or even harmful. This is an
example of "Because you can, does not mean you should". You should know about the options,
but don't use it until absolutely necessary. Even then, proceed with cautions.

Now let's go with the recommended way. Using official APIs is better in almost every way ­ it's
supported, it is backward compatible, it takes care of the cache and any database schema changes,
so you don't have to. It's also much more flexible than the above approach, so for example if you
only want to update prices for products from specific provider, you can easily do so. It's, in most of
the cases, fast enough.

To update prices of all products, we should go with recursive approach ­ given a starting point, we
will get all children. If a children is a product, update its prices. If it is a node, then continue until

Problem 2.5: Split shipments on inventory status

Level: Advanced.

There are cases when a customer places multiple lineitems, and some of them are readily available,
and some are not. Or if they buy one item in batch, but only some of them are in stock, and the
remaining will be fulfilled via backorder. To make the customer happy (and that's what we have
been trying to do, right?), you might want to offer the option to ship as soon as possible. (Patience
is a virtue, but a fast shipping is a source of happiness).

How can we do that?

It's important to keep in mind that Episerver Commerce allows only to ship per shipment. So every
items in a shipment has to be ready (in the inventory) so the all of them can be shipped. To allow
shipping as possible, we need to group all items which are ready into one shipment, and the other
ones to another one.

                 Then the question comes to if you want to ship as soon as possible if some of the (remaining)
                 items become available. You can do the splitting again - however it's up to you. Unless you
                 have very cheap shipping cost, shipping too much can be bad for business, and you don't
                 want to charge the customer for more money once the order is done.

    Things will be more complicated if your customers have multiple shipments. But if you think about
    it, multiple shipments are just shipments to different addresses (and/or different shipping methods)
    - so as long as you keep those information while splitting the shipments, you will be fine.

    The best place to split shipment is probably right before the customer finalize placing an order.

    First we need to find out which items are ready to ship. There are several ways to go, but the easiest
    way in my opinion is to query the inventory to see which items are available. If an item has more
    than in inventory than the ordered quantity, then it'll be in the shipment "number one". If it has
    less quantity in inventory than ordered quantity, then the difference will be moved in the shipment
    "number two".

2 l.Code));

    Note that this will return the inventory records for all warehouses. For economic reasons you would
    not want to ship from a far far away warehouse, so that would make senses to filter the records by
    the nearest warehouse(s). Now we know which items should belong to the second shipment, the
    only remaining thing is to create a new shipment and do the moving.

    In the old days with the concrete APIs, you can use PurchaseOrderManager to move shipment around.

Problem 2.6: Update inventory, the safe way.

Level: Immediate

If you look into the APIs, you might think of it as "simple" - we can just set the inventory to the
new values and be done with it. But is it really that simple?

There are two way to update inventories. When there is usually one source for updating prices (you
would not like end users to update price, wouldn't you?), inventories can be updated concurrently
from multiple sources - multiple customers placing orders at the same time.

And if you just "set" the inventory value, it can be really problematic. What if two customers are
buying same item at the same time. You have 10 in stock. Because customer A is buying 2, you would
set the inventory to 8. But because customer B is also buying, and because the operation starts before
you successfully set the inventory to 8, the thread still sees the inventory as 10, and it will try to set
the inventory to 8. So you are selling 4, but you only reduce your quantity by 2. Except this is not a
magic world and you can't have unlimited stock, so that would end up with some angry customers
because they can't get what they ordered (or at least, have to wait for back order).

The race condition above is more common than you might think. It might work in 90% of the cases,
but in 10% of the cases when race condition happens, it will be a really hair-pulling process to debug.

In my opinion, IInventoryService.Update and IInventoryService.Save are bad APIs and should
not have been introduced.

So what is the safe way?

To ensure that the concurrent operations are handled properly, we can either A. do it ourselves.
or B. delegate it to someone who is really good at it. A is difficult, even very difficult if you
consider the case that you have multiple web servers. Handling multi-threads in one machine is
already complicated enough, but handling multi-threads on several machines is another level of
complication. B is easier - if we have someone to delegate it. In this case, we have - SQL Server.

SQL Server is so good at transaction handling that it's hard to write application code to do it ourselves
better than that (and I have no doubt you can be very smart and experienced). Not only that, you (in
most of the cases) only have one SQL Server instance to handle database transactions from multiple
servers, therefore SQL Server knows everything needed.
    Chapter 2: Inventories and Prices.                                         63

    IInventoryService.Adjust does not set the value directly. As its name might suggest, it adjusts the
    value based on the delta. So if we come back to the example above, when customer A buys 2, you
    don't set the stock to 8, you tell SQL Server to subtract 2. And when customer B buys 2, you tell SQL
    Server to subtract another 2. So in the end, you have 6 left, instead of 8.

    Keep in mind, IInventoryService.Adjust is your friend. Unless you have very, very good reason
    to use Update or Save, Adjust should be your preferred choice.

Problem 2.8: Cancel inventory reservation

Level: Immediate

It's good that your end users place orders with your site. But it's also a reality that for one reason
or another, some of them might want to cancel their orders. While that is not something you would
like, it still happens. How would that be handled?

For most of the cases, if a shipment is already shipped, then the cancellation is not possible, the
buyers would have to wait for it to arrive, then file for a return and a refund. But if shipment is not
yet shipped, things are easier - we can simply cancel the shipment.

But that's only one part of the problem. When the order was made, we reserved the inventories for
the items it contains - so we can be sure we have enough goods to ship. But now the shipment is
being cancelled, shouldn't we cancel those reservations so the inventories can be used for future

    Problem 3.2.3: Performance considerations

    Level: Immediate

    In previous recipes we talked about ReminderSent metafield to ShoppingCart metaclass. Logically it
    should work very well. And you might think it is also fast. You might want to think again.

    In C#, a LINQ query like .Where(c => !c.ReminderSent) can be very fast on a memory-based
    collection. But by using OrderContext.Current.FindCarts, we are querying directly on database -
    in this case ShoppingCart table. Is that query fast enough.

    ReminderSent would be a very ineffective way to filter carts, because it has a very poor selectivity:
    either 0 - false, or 1 - true. SQL Server would have to do a table scan almost every time it needs to
    filter by that column - and an index is useless in this case. If you have big enough number of carts,
    that would be a dead trap for your scheduled job - it will be likely throwing timeout exception all
    the time.

    You might ask then why I added this as an example. Well, the purpose is to demonstrate why an idea
    can be sound and working is not that good. When you work with big-enough dataset, performance
    should always be in your watching list. When a solution is slow, it's not good enough.

    How can we fix it then? We can combine the two solutions we have, by filtering by Modified and
    ReminderSent. We can extend Modified range to make sure we do not miss anything, but we rely
    on ReminderSent to make sure we don't send reminder twice or more.

    The good thing about Modified is that it has a very good selectivity and that makes it a very candidate
    for a non clustered index. When SQL Server see a query which filters on a column with index and
    a column without, it's smart enough to use the index and then filter on the second condition.
Chapter 3: Order                                                                      76

The query would look like this:

1 SqlMetaWhereClause = $"(Meta.Modified BETWEEN GETDATE() - 3 AND GETDATE() - 5) AND
2 Meta.ReminderSent = 0",

  Problem 3.3: Add items to cart

    Level: Beginner
    Allowing customers to place orders is the critical aspect to any e-Commerce sites. In order to do
    that, you have to allow customer to add items to cart, first. This actually consists of two parts, under
    the hood: create/load the cart, then add new item to it. This could be done with CartHelper like this:

1 var cartHelper = new CartHelper();
2 cartHelper.AddEntry(entry, quantity);

    However, CartHelper is dead. In the upcoming Commerce 11.6.1, CartHelper will be obsoleted,
    meaning that you should not use it in any new code, and you should update your code to use the
    new abstraction APIs as soon as possible.

                     You might wonder why CartHelper is dead. It has the bad reputation among developers
                     because it's ver hard to mock, so it's almost impossible to write unit test, or if you want
                     to have your own implementation of cart (i.e. if you want to store the carts else where
                     instead of to the default location). One example of the limitation is the new cart system
                     - the SerializableCart. By saving carts to a separate table and eliminate all unwanted
                     joins, the new cart mode can provide 3-5x performance gain over the default one. However,
                     CartHelper is too tightly-coupled with the default implementation, it's impossible to use
                     SerializableCart with CartHelper. If you are using the new abstraction APIs, switching to
                     SerializableCart is just a matter of a flag in configuration (migration data is still needed,
                     however)

    As a matter of fact, if you start your new Commerce project today, you should be using the
    abstraction APIs (using the latest version available is also a given). The APIs are built around
    IOrderRepository, and its extension methods. Here's how we do it today:
Chapter 3: Order  77

1 var cart = _orderRepository.LoadCart<ICart>(_customerContext.CurrentContactId, name,\
2 _currentMarket);
3 var newLineItem = cart.CreateLineItem(newCode, _orderGroupFactory);
4 newLineItem.Quantity = quantity;
5 cart.AddLineItem(newLineItem, _orderGroupFactory);

    We need to create an ILineItem instance. But instead of using a concrete constructor, we use the
    CreateLineItem extension method. To simplify things, we only set its quantity, then add it to the
    cart by another extension method: AddLineItem.

                     There are many useful extension methods for IOrderGroup, therefore we can use them with
                     ICart and IPurchaseOrder.

There are many things we don't talk about right here, and I would like to ask you to figure out as
practices:

   · We didn't save the cart. The changes to the cart need to be persisted by using IOrderRepository.Save.
   · We are assuming that a cart existed for the current customer, with the specified name,

      and in current market. What if there was no cart? You would need to create it by using
      IOrderRepository.Create<ICart>. Note that there is an extension method for IOrderRepository
      named LoadOrCreate<ICart> which creates carts if none exists. That sounds to be equivalent
      when you call new CartHelper(), but actually it is not. When you call LoadOrCreate, the cart
      is only saved when you save explicitly. When you call new CartHelper(), a cart is already
      created in database. That's why the new abstraction APIs can yield better performance.
   · We did not consider the case when customers add an item to cart when the item is already
      in the cart. In this case, we should not create new ILineItem instance, but to find the existing
      item, and update the quantity.

Problem 3.5: Migrate carts when users log in

Level: Immediate

You of course want all of the visitors to be registered and logged in on your site - there is nothing
better than having recurring customers. But more often than not, your customers might have
registered, but currently not logged in when they are buying stuffs. At some point, they remember
that they have to log in to use the saved shipping addresses and payment options.

What would happen with the items already in the carts?

By default, all the items in the anonymous cart will be merged with the existing items in the "logged
in" cart. Which means, if the customer had item A, quantity 1, and item B, quantity 1 from previous
logged in session, then as an anonymous user, he or she adds item B, quantity 1, and item C, quantity
1 to the cart, the logs in. The cart will now contain item A, quantity 1, item B, quantity 2, and item
C, quantity 1.

In most of the cases that would be a reasonable and expected thing to do. But each business has its
own requirements, and it's nothing strange if you would want to have another behavior. What if
you want to anonymous cart to overwrite the existing cart. In the example above, that would mean
the cart after logging in only contains item B, quantity 1, and item C, quantity 1.

Problem 4.1: Reindex entries when there are changes.

Level: Advanced

When you make changes to an entry, you want it to be reindexed as soon as possible, to the changes
will be reflected in the search result. For example, if you create a new T-shirt with red color, you
would want it to appear when customers filter by red. Right?

There are several ways to do it:

   · To use the event-driven indexing mechanism. In an ideal world, this means you don't have to
      do anything - it will just work for you. Unfortunately, we are not living in an ideal world, and
      while the event-driven indexing can work to some points - and sometimes it stops working.
      And when it stops working, the only option is to restart the site. This instability makes it a less
      favorite option. You can try, but when you run into problems, you have very little control.

   · Full index, which means you throw away every thing, and rebuild the index from scratch. As
      its name might imply, this is an expensive operation, it will consume a lot of time and resources,
      and should be used only when absolutely necessary - for example when you deploy your site
      to a new environment. For our requirements, this does not fit.

   · Incremental index, which only indexes the changed entries. That does sound like what we
      need, but unless if you are using Commerce 11.4 or later, there are several limitations with this

   Problem 4.1.3: Remove entries from index

   Level: Immediate
   When an entry is deleted, we need to make sure its index is removed. You would not want it to
   appear in the search result, wouldn't you?
   Listen to CatalogEventListenerBase.EntryDeleted is a fairly easy part, but how to delete an entry
   from the index? In previous example, we can call SearchManager.UpdateIndex to update index of
   an entry, but it's not deleting, right?

                    It is a pretty well known pattern to listen to -Deleting event, instead of -Deleted event -
                    when you need to react for a deletion. -Deleted event is fired after the item was successfully
                    deleted, and at that point it might be too late to do anything. However in this case we don't
                    need the item, we only need the id, which is provided in -Deleted event.

   Then how?
   The responsibility to delete an index (or actually, a document) does not belong to SearchManager,
   but rather, the IndexBuilder(s). Actually when you call UpdateIndex, SearchManager delegates the
   work to the IndexBuilder(s), SearchManager.UpdateIndex is just a convenient way to do it. We just
   don't have a short cut to delete a document. Let's create our own.
   Normally you only have one IndexBuilder configured, but technically you can have more than one.
   Luckily for us, those are exposed via SearchManager.GetIndexBuilders.
   Chapter 4: Events                                                            93

1 public override void EntryDeleted(object source, DeletedEntryEventArgs args)

2{

3   var id = args.EntryId;

4   var searchManager = new SearchManager(AppContext.Current.ApplicationName);

5   foreach (var indexBuilder in searchManager.GetIndexBuilders())

6   {

7      indexBuilder.DeleteContent("_id", (string)id);

8   }

9}

   Problem 4.3: Update when there are updates

   Level: Immediate

   Your products might be updated from different sources, and for such reason you would want to have
   a central point to take actions when a product is updated. This is a dummy example: whenever a
   catalog content is updated, you want to make sure it has the "Edited" postfix attached to its name.
   Of course this is not a real world scenario, but it's easy to understand the way to do it.

   As usual, the best solution is to listen to events and react: And there are two way to listen to catalog
   content events: IContentEvents and CatalogEventListenerBase. In most of cases, if you are using
   content APIs, you should go with IContentEvents instead.
    Chapter 4: Events                                                                                   95

         IContentEvents works on a higher level than CatalogEventListenerBase: IContentEvents
         is at content level, while CatalogEventListenerBase is on DTO and metaobjects level. which
         means if you are using lower level APIs, such as catalog import export APIs to update catalog
         items, events in IContentEvents will not be fired.

         Previous CatalogEventListenerBase only fire events for changes in DTO, but recently
         metaobjects changes fire events as well.

    IContentEvents works in term of pipeline. So if you are listen to events before the data changes are
    committed, for example, PublishingContent, you are actually editing the content being published.
    For that reason, you don't have to create a writable clone, nor to save it explicitly. The pipeline will
    handle that for you.

    Problem 4.4: Reindex when stock level reaches a
    threshold

    Level: Immediate

    In previous recipe we talked about react to inventory events. One of the most notable application
    for such listener is to reindex the entry when inventory changes. However, that has a drawback:
    inventories can change frequently, especially when your product is selling like hot cakes. In such
    cases it would not make senses to reindex your product every time: it is a waste of time an resource.

    threshold is 10, you don't know if it was changed from 11 to 8 (which should trigger reindex), or
    just from 9 to 8 (which should not trigger reindex). To know if you should reindex or not, you must
    know the delta values.

possible. "Fast" actually consists of two things: the absolute performance (which can be measured by
benchmarks), and the relative performance (which is perceived by the customers). There are several
ways to ensure great performance, and we will get into them later, but in this recipe, we will look
into how to build a fast category page.

If you are new to Episerver Commerce, it would be quite natural for you to build a website
corresponding to the catalog structure. So customers will visit the root page, which lists the catalog,
when they open a catalog, it lists the category, and so on and so forth. And behind, it would also
be natural to build that feature by IContentLoader.GetChildren. It maps between the UI and the
underlying API philosophy, it's easy to understand and it's easy to implement. But is it fast.

It might have decent performance, if you consider that contents are cached by default, so you only
have to fetch something from the database the first time. But a lot of database accesses will still take
time and resources, and in extreme cases it can take your whole site down to its knees. It's safe to
say that if you use search APIs, or content APIs for end-user facing search features, you're doing its
wrong.

The better way to implement category is to avoid accessing database altogether. This can be done
by using the search provider. The search provider system is basically built on indexed search, so a
search on it is very cheap, and usually, very fast, as no database access is needed.

The idea of using search system for product listing is to make sure we have the "path" (or "outline")
included in the index. When we need to list products in a node, we just need to build its path, and
use that path for getting products.

The first part is already done automatically for any search provider, if you do not override neither
BaseCatalogIndexBuilder.IndexCatalogEntryDto nor BaseCatalogIndexBuilder.BuildPath.

                 In previous versions of Commerce, the paths does not contain the "linked" path. Only
                 true children of a node would be listed when searching by outline. Episerver fixed that
                 in Commerce 11.6.

    Problem 5.5.2 Better partial indexing

    Level: Advanced

    In previous we talked about how to only index entries belong to certain categories. It works, however,
    with a drawback. By not indexing something, we make them not-searchable, even for the editors.

    Level: Beginner
    In its most simple form, each promotion can have one coupon code. The base class of all promotions,
    PromotionData, has a block of type CouponData. To set a coupon for a promotion, simply set the

   Problem 6.4: Get coupon code statistics

   Level: Immediate

   In previous recipe we talk about multiple coupon codes promotion. And one of the reasons you would
   want to do that is to have a A/B testing, with each coupon code for each channel of marketing, you
   can see which channel has the best reach to your customers.

   Now you have that promotion. And after a successful campaign, the next essential step is to validate
   how many orders each channel gives you. How?

   Every promotion which was applied (actually redeemed or not) was recorded to a PromotionInformation.
   The collection of PromotionInformation can be accessed via IOrderForm.Promotions.

   Each PromotionInformation contains a coupon code used for that specific promotion, but you would
   not want to load and check every order to make see if a specific coupon was applied - that would
   be a very resource intensive task and can be very slow.

   Commerce has the built-in PromotionInformationRepository, however it is used to get the redemp-
   tion available, so it can't help us with this. That means we have to build something our own - and
   that would include direct database access.

                    In most of the cases, direct database manipulation is strongly advised against, because it can
                    be dangerous and you might damage your data. Direct database query is much more "safe",
                    but it is not without drawbacks. Episerver does not disclose the database schema, so it can be
                    changed without notice, and that means your direct database access code can break even in
                    a non-major update. That however does not happen very often, and you have to consider if
                    the performance benefits outweighs that drawback. It is advised to not use this in a mission
                    critical features or make sure to test them before deploying to production after an upgrade,
                    or both.
Chapter 6: Promotions.                                                                        131

If you look into PromotionInformation table, you can see what we have, and what we need - the
PromotionGuid and CouponCode should be the input, and OrderFormId is the output.

Normally we only have the ContentReference of the promotion, so we can load it by IContentLoader.Get,
which return an instance of the promotion type, and we can get the ContentGuid from there, which
is the PromotionGuid we need. The only remaining thing is to write a query to access the data.

1 SELECT COUNT(OrderFormId) AS TotalCount, CouponCode
2 FROM PromotionInformation
3 WHERE PromotionGuid = @ContentGuid
4 AND IsRedeemed = 1
5 GROUP BY CouponCode
6 ORDER BY TotalCount DESC

Here we are returned the total number of order form which successfully redeemed the promotion,
per coupon code. We order by the TotalCount so the result looks nicer.

This is just the basic information, you might want to get the total spent on the orders for each
coupon. It's as simple as a JOIN to OrderForm table, then SUM(Total)

Here is we talking about the simple (and most common) scenario when each order has only
one OrderForm. Some sites, especially B2B setups, you might have more than one OrderForm
per order. However, in that case, the query above is still correct, depending on how you see
what is counted as "one". If you only see an order is counted as one, no matter how many

Problem 7.4: Shared cart within organization

Level: Immediate
This is a question I get from time to time: An organization might have multiple contacts within it.
All the contacts should share the same cart, so one user can set it up, another approves and places
an order from the cart.
How can that be done?
Each cart is identified by a customer id, name and the market that the cart is in. Customer id is,
suprises, suprises, just a GUID. Which is, conincidently, just the same type as the organization id.

                 That is actually not a "conincidence". Both contact and organization are, essentially, Business
                 Foundation objects. All Business Foundation objects have a GUID as the identity.

Fortunately, the order system is not picky about the GUID used to identify the cart. It does not need
to belong to a contact. So we can just use the organization id for our purpose. Now it's just a little
code to make it work!

                 Carts can belong to anonymous users, that's why it has no hard restriction that the customer
                 id has to belong to a contact.

To make this works, we intercept the IOrderRepository to load the shared cart if the current user
belongs to an organization, otherwise we fall back to the default behavior (load the cart that belong
to the user).
We will talk more about intercept pattern in the next chapter, so in this recipe we will focus
on the main code that actually does the work, not the code that let our code be used. Our
focus should be IOrderRepository.Create<TOrderGroup>(Guid customerId, string name) and
IOrderRepository.Load<TOrderGroup>(Guid customerId, string name).

    Well, that's basically it. We check if a customer belongs to an organization (by simply check if their
    ContactOrganization for null), if yes, then we create the cart/order for the organization, or load the
    carts/orders created for the organization instead.

    We don't have to care about saving the cart, because when you save a cart via IOrderRepository,
    you don't need to supply a "contact id", the current one will be used: the contact who is saving
    the cart does not need to be the one created it. (Which totally makes sense, because otherwise the
    Customer support won't be able to update carts created by customers).

         True, by adding more code, we should expect this to have performance implications. How-

         cost for loading it should be quite minimal. As a rule of thumb, setup and run performance
         tests to see if the performance drop is something you are happy to trade off.

         In this recipe, we only care about cases when users belong to an organization always work
         on their shared cart, which is the most common one. But if you want to allow those users
         to choose between their "corporate" carts and their personal carts, things are a bit trickier.

changes to those classes even without a major release.

Now in many cases, you don't want to replace the entire default implementation, but just parts of
it. There might be several ways to do it. You can try inheriting the default implementations as we
mentioned above - if you are lucky enough that the method you want to override is virtual, with
the risk of having your code broken in a minor update. If the method you want to override is not
virtual, things can be much trickier - you can, technically, reflecting the entire class and copy the
source code, then modify it yourselves. Then you are getting into grey area because that might not
comply with the EULA, but I know some customers have done that anyway. All in all, those can
work to an extend, but they are not officially supported, and you will be on your own if you run
into trouble. Is there a good way to avoid all of those hassles? Yes, by using the interceptors.

Interceptor is a fairly common pattern when it comes to solve this problem. And lucky for us, by

    Level: Advanced
    Back to the first chapter, we learned about Singleton life cycle, and how to register a class to be
    Singleton. But let's think about this more advanced scenario: what if your class implements two
    interfaces, instead of just one

1 public class MyClass: IMyInterface, IMyOtherInterface

    And what if you want to have only one instance of MyClass to be created, regardless of if you
    are requesting IMyInterface or IMyOtherInterface. Registering their life cycles like this should be
    enough, right?

1 [ServiceConfiguration(typeof(IMyInterface), Lifecycle = ServiceInstanceScope.Singlet\
2 on)]
3 [ServiceConfiguration(typeof(IMyOtherInterface), Lifecycle = ServiceInstanceScope.Si\
4 ngleton)]
5 public class MyClass: IMyInterface, IMyOtherInterface

    But if you test it, you will soon find out that if you request an instance of IMyInterface, the instance
    of MyClass you get is actually different from the instance for IMyOtherInterface.

                     Such problem with life cycle can be incredibly hard to debug on production, so it's good if
                     you design a test to verify your code indeed works as expected.

   This is due to the way IoC framework works - if you register for two different interfaces, then two
   instance will be created. Because you registered for the interface, in this case IMyInterface - the
   IoC framework does not know about it when you register for IMyOtherInterface, because they are
   two different interfaces.

   Then how do we solve this problem, how to make sure that the instance we request for IMyInterface
   and IMyOtherInterface are one?

   That's when FactoryMember comes to rescue. This allows us to specify how to create the instance. By
   making that instance unique, we ensure that there is only one instance shared between registrations.

   To use FactoryMember, we need to add it as a property to the attribute
    Chapter 8: Framework                                                                                     165

1 [ServiceConfiguration(typeof(IMyInterface), Lifecycle = ServiceInstanceScope.Singlet\
2 on, , FactoryMember = "Instance")]

    And then we can define Instance as a static property:

1 public static MyClass Instance

2   {

3      get

4      {

5           if (_instance == null)

6           {

7                         lock (KeyLock)

8                         {

9                            if (_instance == null)

10                           {

11                              _instance = new MyClass();

12                           }

13                        }

14          }

15          return _instance;

16     }

17  }

    To make sure we don't have any unintended instances of MyClass, make sure the constructor is
    private, so no other classes can create an instance of MyClass. We also need a private static _instance,
    and a static read only object for locking.

    FactoryMember will tell the IoC framework to use Instance when it tries to create an instance of
    IMyInterface, as well as IMyOtherInterface, and we already made sure that _instance will be
    initialized only once, even in multi threads scenario.

    And that's it, we now have only one instance for multiple registrations.

    Level: Immediate

    In chapter 4, we talked about adding items to indexing queue. In the chapter 2, we talked about how

   10.2.1: Add the organization, the alternative way

   Level: Immediate

   In previous recipe we talk about how to add the organization name to the order list. By using the
   custom template, we actually ensure a pretty "portable" way. It just works with every solution, as
   long as you deploy the files to their correct location. And you can also reuse the custom template for
   other OrderGroup types, like cart or payment plan, as long as you update the grid definitions. But it
   also means more files, and you need to build the project (or the compiled assembly).

   But it is not the only way to do it. What if I tell if you can do it the other way?

   The reason we need a custom template was because organization name is not a part of a
   PurchaseOrder. But that is something we can simply just "do". PurchaseOrder is just a metaclass
   - so you can just add metafields to it.

   What is needed is to create a metafield of type string - let's name it "OrganizationName" - and add
   it to PurchaseOrder class. You can do it manually, but that can be done programmatically.

   The tricky part is to when to set this value. If you just want to have that for purchase orders, we can
   save that information right after you set the value after calling SaveAsPurchaseOrder:

1 var po = _orderRepository.SaveAsPurchaseOrder(cart);

2 var customerId = order.CustomerId;

3 var contact = CustomerContext.Current.GetContactById(customerId);

4 if (contact?.ContactOrganization != null)

5{

6   po.Properties["OrganizationName"] = contact.ContactOrganization.Name;

7}

8 //Do other stuffs

9 _orderRepository.Save(po);

   And then you no longer need the custom template, just a normal column is enough:

1 <Column width="100" allowSorting="true" dataField="OrganizationName" headingText="Or\
2 ganization"></Column>

    Drawback of this approach is that you would need to ensure the PurchaseOrder has the correct
    metafield every time your site start. If you want have organization name for cart list and payment
    plan list, you would have to do the same. There is no clear better or worse way, it's up to you to
    decide.
